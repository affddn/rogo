# Daily optimizer (SEA 0.0.163)

Open **Character → Daily optimizer** after connecting. **Scan account** reads the authenticated character bootstrap, server clock, mailbox and applicable mode views. It does not send a reward claim, start a fight, match a team, buy anything or tap the phone. Character identity is checked before planning. Account data stays in memory; the UI gets recommendation labels and eligibility evidence, not raw mail, credentials or the private bootstrap.

## Auto run in the web app

Choose **Scan account → Review auto run → Start auto run**. Select rewards only, rewards plus sweeps, or rewards plus fights and sweeps. Zero-price shop listings are a separate checkbox. Review the character, current targets and attempt budgets before starting. The default includes all these supported activity groups, but never premium spending, paid refills or ads.

The browser orchestrates one existing reviewed operation at a time, with a fresh scan between actions. It prioritizes earned rewards (including newly unlocked milestones), free listings, suitable fights, then sweeps. There is at most one fight per reviewed mode family; Arena chooses the weakest eligible returned opponent without a reroll. Power-rated fights must meet the suggested power. Guild Hunt and Baphomet have no power gate. Sweeps target the latest highest clear, stay within the initial reviewed attempt budget and require a decreasing attempt count before repeating. Newly unlocked mode families wait for another review. Campaign progression and invitation-only dungeon assistance have separate controls (below). Full Tower climbing and hosting/matchmaking dungeons remain outside Auto run.

Runs are capped at the chosen action limit (maximum 40) and 10 minutes. **Stop after current request** preserves an in-flight receipt and prevents the next action. Leaving the page cancels subsequent actions; reloads do not resume. A rejection, defeat, session/character change, or uncertain outcome stops the run without replay. Receipts stay in page memory. Only hashed-account daily dungeon quota counters and opaque reservations persist locally; chat, room IDs and credentials are not stored by the assist ledger. A new run needs a new review. This is not a schedule or unattended background worker.

The session-specific scan identity and per-action revision prevent a run from silently transferring to a new connection or replaying an unchanged claim. Gateway requests also observe minimum repeated-command spacing (200 ms) and a five-second minimum heartbeat interval. Browser controller tests cover cancellation, budgets, identity changes, stale claims, stale sweep counts, defeat and uncertain results.

**Rewards:** choose individual rows or review all ready claims (up to 24 per pass). Rules cover 26 reward requests across mail, completed quests and scores, timed quests, passes and sign-ins, existing monthly/first-recharge entitlements, weapon mastery, summon progress, card and Collection Gear milestones, unlocked feature previews, eligible events, guild loot, Arena tiers and team-dungeon achievements. No paid make-up sign-ins, voucher payments, purchases, ad callbacks or invented task progress. Seven other catalog reward commands are explicitly listed in the UI rather than tried blindly. Some accounts or events will return no verified candidates.

**Modes:** one reviewed action at a time. Resource realms and MVP target the next difficulty for fights and the highest cleared difficulty for sweeps. Realm tickets, per-boss MVP allowances, free Tower sweeps, guild membership/history and Arena tickets are checked separately. Baphomet and Guild Hunt use the mode-specific damage calculation; Guild Hunt also supplies real phase counts, stage damage and score. Arena selects a returned opponent without a paid refresh and uses the server's combat result. The SEA replay host handles deterministic realm, MVP, Baphomet and Guild Hunt fights without manual inputs. Tower sweeps are supported, not a full multi-floor run; hosting and matchmaking are not part of the optimizer; the invitation-only assist flow is described below. Zero-price shop listings are reviewed **separately** and never submitted by Claim all. Suggested power is a comparison, not a win guarantee.

**Run behavior:** read the character again after consent and recheck each remaining claim after earlier claims; skip changed targets, stop at a rejection, unresolved fight or uncertain network outcome. The run does not replace a selection or replay a write. A receipt records the confirmed reply and reward contents for each action. After a clean run the browser refreshes the read-only plan; newly unlocked actions need another review. No schedule, background spending, or recurring claim authorization is installed. The explicitly reviewed Auto run policy can accept later free rewards, stat proposals and public dungeon invitations within its fixed limits.

All three calls use the same local-only protections and browser session as [Connect Rogo](../CONNECT.md). POST to the existing operations endpoint: `routine.scan` with an empty payload, `routine.prepare` with the returned scanId and selected keys, then `routine.run` with the exact normalized selection, per-session single-use ticket and explicit confirm `routine.run`. Scan IDs expire after five minutes. A mode attempt cannot be bundled with another action. Browser-supplied protobuf payloads or settlement statistics are never accepted by this workflow.

Rules in `rules.json` can be rebuilt with `python3 build_rules.py <stage-extract tables directory> <decompiled excelConfig/Variables.cs>`. They are pinned to the same SEA build as the action catalog. On a game update, review the official TaskModel, SigninModel, BpModel, EmailModel, collection models, mode adapters and matching config before changing eligibility. Rebuild the [local replay host](../replay/README.md) after source or game-data changes. The routine tests can be run from the lookup client with the same pinned dependencies and ILSpy setup as the gateway tests.

## Campaign and class progression

Auto run can now challenge the current campaign boss and advance after a confirmed victory, up to the reviewed boss limit (default five; maximum ten). Each stage is tried once per run, with real server combat inputs and the pinned battle engine. A defeat, missing stage advance or uncertain result stops the run; it does not grind repeated losses.

The **Class branch** control binds the run to one chosen branch. Keeping the current branch never silently switches to another family. A selected alternative can use the official same-tier Job Switch and unlocked specialization switch, then advance only after every class-transfer task reward is claimed. The runner verifies class-change replies and stops if another client changes the class mid-run. It does not claim that a selected class is globally optimal, and does not reallocate saved skills.

**Stat allocation** defaults to unused points. The optional rebuild sends a reset followed by the exact reviewed allocation as one step; its receipt preserves the reset if the second request fails. Budgets and response attributes must match. A build is reset at most once per run, then newly earned points are allocated without another reset. Recommendations reproduce the pinned `HeroAddStatusPanel` / `AttrPointAllocator` logic, including increasing point costs; they are the game's recommendations, not a damage-optimization guarantee. Before/after primary values appear in the review. Class changes and point spending are explicit run settings, with no paid reset or premium purchase path.

## Progression job (Automation page)

Auto run above is still a bounded, reviewed browser run, not a schedule or background worker. The **Automation** page in the web guide is different: it starts a long-running job inside the local guide's helper (the dev-server bridge) for the connected session. The job keeps going if the page is closed or reloaded; the page only starts it, stops it and tails its log. It ends when you stop it, an optional action or time cap is reached, or the game session ends (disconnect, reconnect, or the helper exits). While it runs, its rescans keep the session past the usual 5-minute idle limit.

Each cycle rescans the account and takes the first item that applies:

1. Ready earned rewards, idle income when due, a free Quick Idle while one is left today, then zero-price listings.
2. Unused stat points on the active specialization, then unspent skill points, then learned active skills that aren't equipped (see below).
3. Class advancement once its transfer-task rewards are claimed (never a Novice's first class choice).
4. The current campaign boss, once per stage and build fingerprint (class, specialization, level, power, stat allocation, skill levels). A defeat is information, not a reason to stop.
5. When stuck on a stage: rebuild stats to the game's recommendation (at most once per specialization per stall), another unlocked specialization on the same line, then another class line through the free Job Switch. Each lever is used at most once per stage until the original build's power has risen by at least 3%; smaller rises only retry the boss on the original build.
6. If no build won, return to the build that cleared the earlier stages.
7. Daily sweeps and mode fights within the scan's own attempt counts; a lost mode fight is not repeated that game day. Optional dungeon assist (off by default).
8. Otherwise wait (30 s up to 4 min) and rescan.

It stops, without retrying, on an unknown or incomplete outcome (timeout, lost connection, incomplete receipt, unsettled fight), a helper-side stop, a change of character, session or realm, a class or specialization change made outside the job, or three consecutive rejections. A single rejected step is not offered again in that run. It keeps the existing limits: one request at a time, the same pacing plus at least 2 s between actions, no premium spending, paid refills, paid resets, ads or purchases other than zero-price listings. Other game actions on the guide are refused while it runs.

**Skills.** Skill points are spent with one `CareerSkillUpReq` (4525), the request the official skill panel sends on Confirm (`HeroSpellPanel.ConfirmBtnHandler`): the active build, the absolute level of every learned skill, and the five loadout slots. The planner places only unspent points, using a port of the game's own `SkillAutoAllocator` (the panel's Recommend button): skills are activated tier by tier in table order, prerequisites first, within the job-level and class-tier gates, then raised towards their maximum. It starts from the current levels, so no skill is lowered and nothing is refunded; there is no skill reset in this job. Each level costs one skill point, nothing else is spent. Once the points are confirmed, `CareerSkillUseReq` (4533, `SkillDeployDialog.SendSaveSpellData`) puts learned active skills into empty slots in the order Recommend uses; equipped skills are never moved. Every reply must match the reviewed levels, used points, budget and slots, or the job stops. A build that still has no skills when it is about to fight (no unspent points, or a build the planner couldn't read) gets a warning in the log.

**Idle income.** The job mirrors the official client's battery-saving mode (`BatterySavingRewardController`, `FightRewardModel`): no fight runs; every `BATTERY_SAVING_KILL_MOB_INTERVAL` (15) seconds of this session the stage's `BatterySavingMob` kills are credited (15 for most stages, 5 or 10 early on). When idle income is due, the helper reads the pending interval count (`OnlineIdleRewardPreReq` 4087) and, if one is pending, sends one `OnlineIdleRewardReq` (4089) with up to four intervals (the client's own rounding) and the kills credited since the last claim, never more than the elapsed ticks allow. Elapsed time comes from the helper's session clock, not the browser or the job. At most one read and one claim go out per 15 s, the same cadence as the client's 15 s count refresh and kill timer; while the job waits it collects on each rescan, which is how waiting can raise level and power. A free Quick Idle (`FastIdleRewardReq` 4095) is taken only while today's free count is below the game's free allowance (one; a monthly-card bonus is ignored), and the reply must show the free counter moved with no paid use, or the job stops. Tickets and diamonds are never used. Offline income arrives with the login data and needs no claim. Daily Auto run leaves both to this job.

What it does not do: reset or re-plan skills that are already allocated, touch gear, cards or pets, or reconnect after a lost session. The decision logic is model-checked and tested offline with a fake game; **it has not been run against the live game.**

## Invitation-only dungeon assistance

Enable **Accept posted dungeon invites**, or use **Review dungeon-assist watch** to run without campaign fights, class changes or daily mode attempts. The helper uses the official client's public-channel subscription bundle (zone, server, guild and the virtual `CHAT_TYPE_TEAM_INVITE` type). Ordinary chat is discarded; only structured public dungeon invitations are retained in memory. It never posts a message, hosts a room, invites a friend, changes chat filters, or joins a private unsolicited invitation. It filters the structured invitation fields, the 45-second game expiry, unlocked stages and suggested power. The server's stage-unlock read is checked again before joining.

A reviewed invitation runs the full sequence: join its room → confirm **Assist only** → wait up to 40 seconds for that host's start notification → read that team's fight inputs → simulate the real three-player dungeon → submit the correlated settlement → leave that room. A start packet alone is not success. No normal clear attempt is authorized; a successful assist must have reward type 1, an increased server assist count, the same game-day reset stamp and an unchanged normal-clear count. Team/stage/assist-setting changes stop the workflow. A host start received before Assist-only confirmation also stops without submitting a fight. Existing parties are not replaced or left.

The limit is **five per server game day**, including assists already completed through another client. Before every join, an atomic locked ledger reserves one slot. Successful server-confirmed assists replace the reservation with the server count. A clearly rejected join releases its reservation; a room timeout keeps it as an accepted invitation. Unknown join/settlement outcomes keep a reservation and disable further auto-joins for that day rather than risk exceeding the cap. The ignored local ledger is under `data/automation/dungeon-assists/`, keyed by hashed realm/player identity and server `last_reset_time`, so reloads and reconnects do not reset the cap. Do not delete it to retry an uncertain action.

While no eligible invite is available, the browser waits and rescans within the existing ten-minute/action limits. Stop interrupts that wait; an in-flight assist completes its current bounded workflow before stopping. Reload and leaving the page do not resume or install a background schedule. Five is a cap, not a promise that five eligible invitations will arrive or that every party will win.

Offline checks cover quota persistence and reservations, rejection and timeout behavior, Assist-only gating, room ownership, packet notifications after replies, three-member pinned-engine replay, point budgets, class gates, campaign sequencing and browser cancellation. Live coverage is recorded separately; unit tests and replay fixtures are not live server acceptance.
